组件与容器采集模块设计 融合设计稿 · 未实现

状态：融合设计稿（未实现，2026-08-14 更新）。本文档以当前已经落地的动态注册表、跨平台 Provider、Nmap 风格命令、依赖编排和批次协议 2.0 为内核，补充「服务 / 包 / 容器 / 文件 / 组件 / 应用」能力，遵循同一套模块化、故障隔离、证据链与稳定标识原则。

规范源：本仓库当前以这份已跟踪 HTML 为组件与容器设计的唯一实现依据；如本地工作区存在同名 Markdown 副本，其内容不参与实现和验收，后续只有在建立可重复的 HTML 生成流程后才恢复 Markdown 源文件。

已实现模块（host、network、process、port、connection）继续作为兼容基线；本文新增的 service、package、container、file、component、application 均属后续阶段，当前协议不为其输出伪空字段。扫描器内核现已支持“软依赖自动编排但不阻断”，新增模块无需重写 CLI、Provider、统一模型或报告层。

范围说明：本文不是扫描器全部模块的总规格。总体路线中的 resource（10 分钟）、filesystem、disk、常驻调度、消费确认和保留清理仍按扫描器总体设计独立实施；本文列出的周期是模块元数据和外部调度建议，当前扫描器不会自行常驻定时执行。

1. 目标

在现有「主机 → 网络 → 进程 → 端口 → 连接」事实链之上，继续向上采集并推导：

  • 服务器运行了哪些操作系统服务（通用服务身份、状态、主进程、启动入口、运行用户；Linux 首版由 systemd Provider 实现）；
  • 安装了哪些软件包（名称、版本、架构、来源）；
  • 运行了哪些 Docker / containerd 容器（镜像、状态、端口映射、挂载、命名空间）；
  • 哪些运行文件、动态库、配置参与了这些进程和服务；
  • 由上述事实推导出组件 / 框架 / 运行时 / 库 / 插件及其版本；
  • 最终聚合为可部署的应用 / 业务实例。

最终产物与既有批次一致：统一 AssetRecord / RelationshipRecord，带 scope_id、states、confidence、evidence，供 CMDB 做漏洞匹配、资产治理与影响分析。

2. 核心原则

2.1 一个采集域 = 一个模块 = 一条命令

每个有独立资产语义、数据源或性能成本的功能都是独立模块，拥有：

命令、输出 record_type、数据源、依赖、降级行为、测试

新增模块实现 Descriptor()/Probe()/Collect() 并注册一行后，自动获得 CLI 参数、进入 scan 全量计划并复用批次输出。除一次性完善软依赖计划语义外，不增加 CLI 模块名分支，不让业务模块直接依赖 Linux 实现。

2.2 事实型模块与推导型模块分离

类别模块特征结论置信度
事实型service、package、container、file数据源单一确定，直接读取通常 exact / strong
推导型component、application依赖规则库聚合、识别exact / strong / inferred，必须显式标注

事实型模块只输出可验证的观测事实；推导型模块基于事实和规则输出结论。证据不足时保留原始事实并在模块状态、Coverage 或错误中记录未匹配数量；只有存在稳定作用域和可追溯证据组合时才创建 unknown_component/unknown_application，不得静默遗漏、批量制造伪未知资产，或仅凭进程名/端口号强行归类。

2.3 证据链：结论必须能追溯到证据

IP 地址
  ↓ network
监听端口和连接
  ↓ socket inode + /proc/<pid>/fd
进程与稳定进程身份
  ↓ systemd MainPID / Cgroup
操作系统服务
  ↓ 容器运行时元数据 / 命名空间
容器
  ↓ 包数据库 + 运行文件 + 清单
软件包 / 文件 / 组件（版本、框架、库、插件）
  ↓ 聚合规则 + 直接证据
可部署应用 / 业务实例

只有直接证据才能标 exact。每一条 AssetRecord 与 RelationshipRecord 都必须携带 evidence（provider、source_type、locator/locator_hash、observed_at、confidence）。

2.4 容器是作用域，不是第二套进程模块

容器内进程仍由 process 统一采集，用关系 process → runs_in → container 关联，不复制第二套进程采集，也不由 container 模块重写 process 记录。进程记录继续使用宿主机作用域和稳定进程 ID；容器归属由 runs_in 表达。文件、包、组件等真正位于容器文件系统内的记录，使用 scope_id + scope_type 标记容器作用域。

2.5 稳定 ID：可变字段不进 ID

record_id 只由不可变/稳定的键生成。版本、状态、端口、哈希等会变化的字段一律放 attributes，否则每次升级都会生成新资产、破坏 CMDB 的「同一资产生命周期」判断。

2.6 故障隔离：依赖用于补证据，不用于放大故障

  • 硬依赖：自动进入执行计划；缺失后目标模块无法形成最基本的稳定身份或任何可信结果，失败时可以阻断目标模块。
  • 软依赖：同样自动进入本次执行计划并去重；失败时目标模块仍消费其它可用事实继续执行，结果降为 partial/degraded、authoritative=false，不得整链阻断。
  • Provider 能力：例如 socket 是底层能力，不是模块名；模块依赖只能引用注册表中的真实模块，例如 port。

当前执行器已经把硬依赖与软依赖都纳入递归闭包和拓扑顺序，并检测未知依赖与硬/软混合环；只有硬依赖失败会阻断目标模块，软依赖失败会使目标结果降为非权威 partial。人工执行模块命令时依赖使用本次新鲜事实；周期调度器应合并同一时点到期模块，使同一数据源在一个批次内只采一次。

4. 依赖图

箭头方向统一为“目标模块 → 依赖模块”；实线为硬依赖，虚线为失败不阻断的软依赖：

network ───────→ host
process ───────→ host
port ──────────→ process ─────→ host             ← 已有
connection ────→ port

package ───────→ host   ······→ container
service ───────→ host   ······→ process
container ─────→ host   ······→ process + port
file ──────────→ process ·····→ service + container
component ─────→ host   ······→ package + service + process + file + container
application ───→ host   ······→ component + service + container + process + port
  • service 使用 process 的进程事实把 Unit 的 MainPID 精确关联到进程；
  • container 使用 process 的 PID 命名空间/Cgroup 判定「进程在哪个容器里」；
  • file 从 process 的 exe/cwd/root/maps 证据链枚举文件，不遍历全盘；
  • component 与 application 是纯推导层，消费依赖模块的 Internal 强类型事实，不新增 Provider。
  • 任何软依赖失败都只降低结果完整性；只要存在可验证事实，目标模块继续输出，不允许因一条证据链断裂而清空其它成功结果。

5. 命令设计

与现有 CLI 完全一致：

# 单模块
sudo asset-agent -service
sudo asset-agent -package
sudo asset-agent -container
sudo asset-agent -component
sudo asset-agent -application

# 组合（依赖自动编排，数据源只采一次）
sudo asset-agent -service -package
sudo asset-agent -container -service -port

# 全量（动态包含全部已注册模块）
sudo asset-agent scan

硬依赖和软依赖均自动编排且在本批次去重；软依赖失败不阻断目标模块。依赖模块照例执行但只发布用户选择模块的记录，其状态仍写入 manifest.json。socket 不是用户命令，不能写入模块依赖或出现 -socket。

6. 公共对象模型

新增模块复用 internal/model/batch.go 的统一模型，不引入新的顶层结构。

6.1 AssetRecord（不变）

{
  "record_id": "stable-id",
  "record_type": "component",
  "host_id": "host-id",
  "scope_id": "host-id",
  "scope_type": "host",
  "name": "nginx",
  "version": "1.24.0",
  "vendor": "nginx.org",
  "platform": "linux",
  "states": {"installed": true, "running": true, "loaded": true, "exposed": false},
  "first_observed_at": "...",
  "last_observed_at": "...",
  "confidence": "exact",
  "attributes": {},
  "evidence": []
}
  • scope_type：宿主记录为 host；容器内记录为 container，scope_id 为 container:<id>。
  • states 四个位必须分别表达：installed（已安装）、running（正在运行）、loaded（已加载）、exposed（存在暴露证据）。已安装但未运行的包/服务/组件仍是漏洞排查对象。
  • 每个模块的具体字段写入 attributes；version、vendor 是顶层字段，包/组件/容器/服务优先使用。

6.2 RelationshipRecord 与 Evidence（不变）

沿用现有 RelationshipRecord（record_id、relationship_type、from_id、to_id、observed_at、confidence、evidence）与 Evidence（provider、source_type、locator、locator_hash、observed_at、digest、confidence）。

7. 各模块详细设计

7.1 service（事实型）

  • Provider 契约：ServiceProvider，能力名 service。
  • 通用契约：模块只认识服务身份、状态、主进程、启动入口和运行身份，不认识 systemd、Windows SCM 或 launchd 的具体调用方式。
  • Linux 首版数据源：systemd D-Bus（org.freedesktop.systemd1）优先；不可用时降级读取 /etc/systemd/system、/lib/systemd/system 的 Unit 文件。未来由 Windows/macOS Provider 映射同一通用事实。
  • 依赖：硬依赖 host 形成稳定归属；软依赖 process，用于 MainPID → 进程记录精确关联。进程采集失败不得阻止服务事实输出。
  • record_type：service。

attributes：

service_manager、native_service_key、display_name、state、
main_pid、exec_start、user、group、description、
unit_name、unit_state、load_state、fragment_path、enabled_state（Linux systemd 扩展）

states：installed（Unit 存在）、running（active）、loaded（已加载）。

关系：

关系类型方向语义置信度
runs_asservice → processUnit 的 MainPID 对应进程exact（MainPID + /proc/<pid> 直接证据）

降级行为：D-Bus 不可用时读 Unit 文件 → 状态降为 partial，MainPID 无法解析时 runs_as 关系缺失，service 记录保留 installed/loaded 事实并标注 partial。

7.2 package（事实型）

  • Provider 契约：PackageProvider，能力名 package。
  • 数据源：Provider 按平台选择包数据库；Linux 首版支持 dpkg（/var/lib/dpkg/status）、rpm 数据库或 apk（/lib/apk/db）。读取时优先走只读数据库解析器，不执行包管理器命令；无法安全解析的 rpmdb 格式必须明确标记 unsupported，不得猜测。
  • 依赖：硬依赖 host（稳定主机 ID）；软依赖 container，用于沿运行时确认的 rootfs 读取容器内包数据库。容器来源失败不得影响宿主机软件包结果。
  • record_type：package。

顶层字段：name=包名、version=版本、vendor=维护者/厂商。

attributes：

architecture、package_source（dpkg/rpm/apk）、
description、installed_size_bytes（可选）

states：installed=true，running/loaded/exposed=false（包本身不表达运行状态）。

关系：不额外生成（host_id 已表达归属）。

降级行为：某种包库缺失时仅记录该来源缺失，其余来源正常；全部缺失 → unsupported。

7.3 container（事实型）

  • Provider 契约：ContainerProvider，能力名 container。运行时元数据由 Provider 采集；宿主端口监听验证消费 port 模块结果，不把 socket Provider 能力伪装成模块。
  • 数据源：Docker Engine API（Linux 首版通常为 /var/run/docker.sock）、containerd/CRI；所有受支持的运行时端点均不可用时标 unsupported。
  • 依赖：硬依赖 host 形成稳定归属；软依赖 process（命名空间/Cgroup 归属）与 port（宿主端口监听校验）。进程或端口采集失败时仍输出运行时 API 能确认的容器与镜像。
  • record_type：container、container_image。

container 顶层：name=容器名，attributes：

runtime、container_id（短 ID，仅展示）、
image_id、image_name、image_tag、
state（running/exited/...）、
ports（[{container_port, protocol, host_ip, host_port}]）、
mounts（[{source, destination, mode}]）、
network_namespace、pid_namespace、cgroup、
labels（脱敏后的关键标签）、restart_policy

container_image：name=镜像名，attributes：

image_id、repo_digest、size_bytes、created_at、labels

states：running（容器运行）、loaded（镜像已加载）、exposed（存在端口映射）。

关系：

关系类型方向语义置信度
runs_inprocess → container进程运行在容器内exact（PID ns / cgroup 直接证据）
based_oncontainer → container_image容器由镜像实例化exact
runs_oncontainer → host容器运行在主机上exact

降级行为：Docker socket 存在但无法访问 → degraded（仅报运行时探测失败）；containerd 存在但 Docker 缺失 → 输出 containerd 源；全部缺失 → unsupported。

边界：首版从宿主机读取容器元数据与 rootfs，暂不进入容器网络命名空间抓取容器内 socket。rootfs 位置必须由运行时 API、快照器或挂载元数据解析，不把 /var/lib/docker/overlay2 等实现路径写死在业务模块；容器内文件读取遵守与宿主机相同的白名单边界。

7.4 file（事实型）

  • Provider 契约：FileEvidenceProvider，能力名 file。
  • 数据源：/proc/<pid>/{exe,cwd,root}、/proc/<pid>/maps（动态库）、服务 ExecStart、组件清单指向的配置文件。只沿证据链读取，不遍历全盘。
  • 依赖：硬依赖 process；软依赖 service、container，用于补充启动入口和容器 rootfs 证据。软依赖失败不阻止沿进程证据链读取。
  • record_type：file。

顶层：name=归一化相对路径（相对 host 或容器 rootfs），attributes：

absolute_path、sha256、mode、owner_uid、owner_gid、
size_bytes、mtime、file_kind（executable/shared_library/config/data）

states：installed=true、loaded=true（若被某进程加载）。

关系：

关系类型方向语义置信度
loaded_byfile → process文件被进程加载exact（/proc/<pid>/maps 直接证据）

降级行为：单个文件读取失败（权限/已删除）→ 记录缺失但保留其它文件，partial；敏感路径（私钥、Token、配置原文）只输出 locator_hash，不输出内容。

性能边界：SHA256 按 size + mtime 缓存，未变化不重算。

7.5 component（推导型）

  • 数据来源：硬依赖 host 建立稳定作用域；以 package、service、process、file、container 为软依赖，消费其中成功模块的 Internal，通过识别规则库推导组件。任一来源失败只降低覆盖率，不阻断其它来源。
  • 无新 Provider：是纯推导模块。
  • record_type：component。

顶层：name=组件名、version=版本、vendor=厂商。

attributes：

ecosystem、purl、cpe、
package_source、artifact_digest、
detected_by（规则名）、version_source（包库/清单/banner/名称）

states：installed（来自包/文件）、running（来自进程/服务）、loaded（来自动态库/清单）。

关系：

关系类型方向语义置信度
provided_bycomponent → package组件由软件包提供exact/strong
consists_ofcomponent → file组件由文件构成strong/inferred
uses_componentprocess → component进程执行或加载该组件exact/strong/inferred

service → component 的关系不重复采集，由 CMDB 沿 service →runs_as→ process →uses_component→ component 推导。

降级行为：规则库缺失 → 模块 degraded 且不输出推导资产；规则无匹配 → 保留原始事实并记录 unmatched_count，不默认给每个进程制造 unknown_component。只有具备稳定作用域和至少一条可追溯组件证据、但名称仍无法归类时才输出稳定的未知组件。版本无法确定时 confidence=inferred 且 version 留空，不作为漏洞匹配唯一依据。

7.6 application（推导型）

  • 数据来源：硬依赖 host 建立稳定作用域；以 component、service、container、process、port 为软依赖，消费成功模块的 Internal 并按聚合规则归并。单一来源失败只降低置信度和覆盖率。
  • 无新 Provider：纯聚合模块。
  • record_type：application。

顶层：name=应用/部署名，attributes：

deployment_name、namespace、environment（生产/测试/UAT，可选）、
service_units、container_names、component_names、exposed_ports

states：running（任一进程/服务/容器在运行）、exposed（存在监听/端口映射）。

关系：

关系类型方向语义置信度
consists_ofapplication → component应用由组件构成strong
deployed_asapplication → service应用以服务方式部署exact
runs_inapplication → container应用运行在容器内exact

降级行为：聚合证据不足时保留已确认的组件、服务、容器、进程和端口事实，并记录未归属数量；只有存在稳定部署边界（例如 Unit、容器/编排标签、部署目录或用户资产标签）时才输出 unknown_application，不得仅凭进程名强行归类。

9. 稳定 ID 约定

record_id 统一用 StableRecordID(recordType, parts...) 生成，parts 只含稳定键：

类型稳定键明确不进 ID 的字段
hostDMI UUID（回退 hostname）—
processboot_id:pid:starttime—
servicehost + service_manager + native_service_key（Linux 为 unit_name）状态、MainPID、显示名
packagehost + 架构 + 包名版本
containerhost + runtime + container_id容器名、状态
container_imagehost + runtime + image_id/repo_digesttag、size、loaded 状态
filescope + 归一化相对路径sha256、mtime
componentscope + ecosystem + 名称版本、purl 里的版本段
applicationscope + 部署名 + 命名空间端口、组件清单

铁律：版本、状态、端口、哈希等可变字段只入 attributes，绝不入 record_id。

10. 证据等级与版本提取

confidence 统一为 exact、strong、inferred、unknown：

exact    包库条目、systemd ExecStart 指向的二进制、清单内直接版本号
strong   版本文件直接读出（java release、package.json、go buildinfo、Ruby gemspec）
inferred 进程名/端口/路径名推定（如 "java" 进程 → JVM 存在，版本未知）
unknown  无任何可验证证据

版本提取可靠性：包数据库 > 版本文件/清单 > 运行时指纹(banner/cmdline) > 名称推断。inferred/unknown 不能覆盖 exact，也不能作为漏洞匹配的唯一依据。

11. 容器 scope 设计

  • 容器内进程由 process 统一采集并保持宿主机作用域；container 根据 /proc/<pid>/ns/pid、cgroup 和运行时元数据补充 runs_in 关系，不复制或重写进程记录；
  • 容器内文件/包/组件记录使用 scope_type="container"、scope_id="container:<id>"；
  • 容器 rootfs 由 ContainerProvider 通过运行时 API、快照器或挂载元数据定位；业务模块不固定 Docker 数据目录或存储驱动路径，并遵守与宿主机相同的白名单边界，不因能访问容器 rootfs 而扩大读取范围；
  • 首版不进入容器 netns 抓取容器内 socket；容器暴露端口由运行时 API 的端口映射表达，宿主监听状态由 port 模块交叉验证。

12. 组件识别规则库

规则库与代码分离，内置一批可扩展规则（后续可外置为配置文件）：

- id: nginx
  ecosystem: web-server
  vendor: nginx.org
  match:
    package_names: ["nginx", "nginx-core"]
    process_names: ["nginx"]
    files: ["*/sbin/nginx", "*/nginx"]
  version_from:            # 版本提取来源优先级
    - {kind: package}
    - {kind: file, glob: "*/nginx", regex: "nginx/([0-9.]+)"}
    - {kind: banner, regex: "Server: nginx/([0-9.]+)"}
  cpe_prefix: "cpe:2.3:a:nginx:nginx"

每条规则声明：match（包名/进程名/文件/端口特征）与 version_from（版本来源与正则）。采集器统一执行，缺证据时标 inferred。规则命中即产出 component；不命中则保留原始事实、不硬编码 switch。

13. 性能与安全边界

  • 不执行 Shell；不读取 /proc/<pid>/environ；不读取私钥、Token、密码、配置原文；
  • 只沿进程/服务/容器/包/组件证据链读取文件，不遍历全盘；
  • 文件 SHA256 按 size + mtime 缓存，未变不重算；
  • 敏感路径只输出 locator_hash；
  • 重型模块（file、component、application）并发数保持 1，避免多模块同时遍历进程/容器；
  • 手工执行单模块时，本批次自动依赖只采一次；周期调度时合并同一时点到期模块，避免 component/application 重复触发相同事实源；
  • 模块周期只是调度建议：service/container 12h，package/file/component/application 24h；更高频的 resource 10 分钟、port/connection 1h、network 6h 按总体设计独立调度。
  • 脱敏在进入统一模型前完成（security.RedactArgs 等），输出层不承担首次脱敏责任。

14. 分阶段实现

阶段1（已完成） host/network/process/port/connection + 内核（含软依赖计划与非阻断降级）
阶段2  service + package        ← 数据源确定、结论可靠，先增加事实源
阶段3  container                ← Docker/containerd，中等复杂度
阶段4  file + component         ← 先补文件证据，再实现规则推导
阶段5  application              ← 聚合，依赖前面全部，最后做

建议先落地 service + package：数据源单一、结论可靠，能立刻给 CMDB 带来「服务清单 + 软件清单」两大价值，也最容易验证模块化扩展路径。

15. 测试与验收

每个新模块必须覆盖：

  1. 注册后自动获得 -<module> 参数并进入全量 scan；
  2. 依赖编排正确：硬依赖与软依赖均自动进入计划并去重；软依赖失败时目标模块继续执行并降级，硬依赖失败时按约定阻断；
  3. 单模块只发布目标模块记录，依赖模块状态写入 manifest；
  4. 字段、states、confidence、evidence 与关系类型稳定；
  5. 降级行为：数据源缺失 → partial/unsupported，不产生伪空记录；
  6. 稳定 ID：版本/状态变化不改 record_id；
  7. 容器 scope：进程保持宿主作用域且具有 runs_in 归属；容器内文件/包/组件的 scope_type 正确；
  8. 规则库：命中、未命中、版本提取三种路径；未命中时不批量制造伪 unknown 资产；
  9. 稳定 ID 隔离：不同主机出现相同 container/image ID 时不会碰撞；
  10. 跨平台边界：业务模块测试使用通用 Provider 假实现，不直接导入 systemd、Docker 或 Linux 路径；
  11. 安全边界：不读 environ、凭据脱敏、不遍历全盘；
  12. 最终 go fmt、go vet、go test ./... -count=1 与 Linux 静态构建验证。
